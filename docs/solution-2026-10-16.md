# The solution, 2026-10-16: Windows's own code as the specification

**History from 2026-10-16:** superseded by `docs/plan.md`, the one live direction document (full review `docs/review-2026-10-16-full.md`, item 6; BLACKBOARD Decisions, 2026-10-16 user).

The requirement (user decisions of 2026-10-16, BLACKBOARD): w2m runs any Windows game on a Mac, at speed, and finds by
running only what no file, header or specification states. This document is the solution worked out before any of it
is built. Each layer gives its knowable source, its edge (what is left once the source is used), the design, the
judge, and the questions only an experiment can settle, each with the result that settles it. Revised the same day
after a review; section 9 lists what the review changed and what was checked.

## 1. Why the project was slow

w2m rewrote Windows. It wrote 338 Windows functions by hand in the guest runtime, one game stop at a time, against
120,902 exports in the laptop's System32 alone. A rewrite of Windows must match Windows's behavior, quirks included,
and nothing tells it what that behavior is except running Windows. That is why each function took a stop and a probe.

The behavior is not secret. It is whatever Windows's code does, and that code is on the laptop's disk. The
documentation is incomplete; the binaries are not. So w2m runs Windows's own user-mode DLLs, translated like game code,
and writes only what lies beneath them. Every exported function then behaves as on Windows because it is Windows's
code.

There is precedent. Microsoft Research's Drawbridge ran Windows 7's user mode, Excel, PowerPoint and Internet Explorer
among it, on a small host interface (Porter et al., ASPLOS 2011). Drawbridge had Microsoft's source and moved much of
the NT personality into its library; w2m has neither, and takes the kernel's interface as Windows ships it. Wine does
the opposite: it rewrites user mode, and its own documentation says native kernel32 and ntdll "will never work" under
it, because they need kernel access Wine does not provide. w2m supplies that access; that is the whole difference.

## 2. The frontier, re-aimed

The frontier is not retired. Its method stays (run until the first difference from Windows, record it, enter the
answer), and only its boundary moves: from the 120,902 exports to the edge below Microsoft's DLLs. Its stops become
three kinds of difference against the laptop: a system call (number, information class, arguments, result), a
win32k call, and a display-driver interface call. Everything a file, header or specification states is entered
before the first run (E2's census); the frontier finds only the residue, as the user decided.

The frontier gets the tools the research paper (`docs/research-paper-growing-a-runtime-from-observation.md`) names
for it: snapshots of the VM at each stop, forking a run from a snapshot to try an answer, and the laptop as the oracle
that answers the question each stop asks.

## 3. The input: all of Windows, copied once

What the copy at `~/w2m-depots/windows-system` holds today (checked 2026-10-16): System32 (3,415 DLLs) and SysWOW64
(2,268), `clsid.reg`, `interface.reg` and `build.txt`; 2.6 GB. It holds no executables (0 `.exe` files: no csrss,
dwm, svchost or conhost), no registry hives, no WinSxS, and no list of KnownDlls. It does hold `apisetschema.dll`.

That copy is a slice. The first draft of this document claimed the hives had been "exported once, as System32 was";
they were not. Under the standing rule (acquire whole inputs), the first act of this plan, before any experiment,
copies the whole of the laptop's `C:\Windows` (System32, SysWOW64, WinSxS, every executable) and saves the `SOFTWARE`
and `SYSTEM` hives (`reg save`), with the build number, into the depot. E1 would otherwise ask for each piece in turn,
one stop at a time.

## 4. The layers and their edges

| Layer | Taken from | w2m supplies (the edge) |
|---|---|---|
| CPU | Intel's manual; the decoder's spec rows | the translator (x86 and x86-64 to arm64) |
| Windows user mode (kernel32, kernelbase, user32, gdi32, advapi32, ole32, ...) | Microsoft's DLLs | nothing: they run as they are |
| The NT kernel | the system call stubs in ntdll.dll and win32u.dll | the system calls and their information classes, the state the kernel builds, the kernel-to-user entries |
| Windows processes (csrss, DWM, services) | ReactOS's csrss messages; Microsoft's presentation and audio docs | csrss's messages; presentation to a Metal layer; WASAPI on Core Audio |
| Graphics | Direct3D 9-12 runtimes; the WDK's driver interfaces; the shader formats | one user-mode display driver that draws with Metal; presentation |
| Devices and Steam | Microsoft's and Valve's DLLs over them | the device interfaces; the Steam client's interface |

The count, taken before this plan: ntdll.dll's x64 stubs carry 488 distinct system call numbers (977 stubs, Nt and Zw
names); win32u.dll's carry 1,486. That count undercounts the kernel's surface. One call can carry dozens of
information classes (NtQuerySystemInformation, NtQueryInformationProcess, NtSetInformationThread), each with its own
structure. The surface is calls times classes, and E2 sizes it.

### 4.1 CPU

- **Source.** Intel's SDM; `specs/x86_decode.json` (1,067 rows); the rules in `src/w2m/rules`.
- **Design.** As decided (Decisions of 2026-10-16): the compiler generated from the rules, its control in C and each
  op's lowering as stencils made by running the Python on symbols; a 32-bit decoding mode in the decoder and the rules,
  in the IR's key from the start; the model's slow paths (x87, SHLD/SHRD, RCR, the flag and string forms) lowered
  natively. Microsoft's DLLs are x86-64 code like the game's, so they need nothing new of this layer; they raise its
  volume.
- **Judge.** The class runs against Intel's recorded results; word equality of the generated compiler with
  compile_insn.

### 4.2 Windows user mode

- **Source.** The DLLs. kernel32 forwards to kernelbase; user32 and gdi32 call win32u's stubs; everything reaches the
  kernel through ntdll or win32u, or another process through ALPC.
- **Design.** w2m loads them as Windows does: the kernel creates the process (its PEB, its first thread's TEB and
  stack), maps ntdll and the image, and starts the thread at ntdll's `LdrInitializeThunk`; ntdll's own loader then
  maps every DLL through system calls. `src/w2m/loader.py` gives way to ntdll's loader (section 5), and w2m does what
  the kernel does before the first instruction.
- **The state the kernel builds before user mode runs.** Three pieces, each named in E1's result:
  - the API set map, which the kernel maps into every process from `apisetschema.dll` and the PEB points to;
  - the `\KnownDlls` object directory of section objects, which ntdll's loader opens before it searches the disk;
  - KUSER_SHARED_DATA, whose time fields (interrupt time, system time, tick count) the kernel keeps updating while the
    process runs; w2m updates them from the host clock.
- **Judge.** Two. First, the 68 families: their rows were recorded on Windows, so Microsoft's DLLs over w2m's kernel
  must reproduce them; the suite exists and runs now. Second, system-call traces against the laptop's (4.3).
- **Open.**
  - **Known, not an experiment: the shape of process start.** It is published: the kernel maps the image and ntdll,
    creates the first thread, and every user-mode thread begins in `LdrInitializeThunk`; ntdll connects to csrss
    through `CsrClientConnectToServer` ("\\Windows", BASESRV_INDEX) and loads the imports (Windows Internals,
    "Processes and threads"; j00ru's CSRSS write-ups; Outflank's 2024 account of process creation). w2m builds to that
    account.
  - E1. *What exact calls does build 26200's start make?* The published account names the steps, not this build's
    call list. Recorded on the laptop, not discovered in w2m: a probe exe's start under DTrace's syscall provider
    (E3). Settled by: the list of system calls with their arguments and information classes before the probe's entry;
    the ALPC ports it connects to. w2m then runs `LdrInitializeThunk` against that list from the first try.
  - E2. *What do the games' imports reach?* For each import the census lists, a static walk of the call graph through
    Microsoft's DLLs (direct calls, import thunks, indirect calls marked) to the system calls it can reach. At each
    call site it records the information-class argument when that argument is a constant. Settled by: per game, the
    set of (system call, information class) pairs reachable, the ALPC ports and RPC interfaces named in the DLLs'
    data, and the count of call edges the walk could not resolve.

### 4.3 The NT kernel

- **Source.** The stubs (names and numbers, per build); the structures' layouts (`specs/guest_state.json` holds the TEB
  and PEB fields probed on Windows, Sprint 034); the parameters of ntdll's exports, which the Windows Driver Kit
  headers and Microsoft's documentation of the Zw routines give for most; the information-class enumerations and
  structures, which the same headers give for many.
- **Design.** A kernel inside the VM, in C in the guest runtime, grouped by the kernel's own managers:
  - memory (NtAllocateVirtualMemory, NtProtectVirtualMemory, NtQueryVirtualMemory; sections: NtCreateSection,
    NtMapViewOfSection) on the VM's page tables;
  - objects and handles (the namespace: `\??\C:`, `\Device\...`, `\KnownDlls`, named events and sections);
  - files (NtCreateFile, NtReadFile, NtQueryInformationFile, NtQueryDirectoryFile) over the host's file bridge;
  - the registry (NtOpenKey, NtQueryValueKey) over the laptop's saved hives as data;
  - threads, synchronization and time (NtCreateThreadEx, NtWaitForSingleObject, events, mutants, semaphores, keyed
    events, alerts, timers) on the scheduler;
  - exceptions and callbacks: the kernel's three entries into user mode, ntdll's `KiUserExceptionDispatcher`,
    `KiUserApcDispatcher` and `KiUserCallbackDispatcher` (window procedures called from win32k);
  - ALPC (NtAlpc*), the transport to other processes (4.5).
- **What the stubs do not say.** A system call's meaning is the kernel's code, which runs in kernel mode
  (ntoskrnl.exe) and is not run here. It comes from three sources, in order: the documented routines and structures;
  what the calling DLLs pass and need back, which E2's walk reads; and the laptop, where each call can be observed. The
  last is the frontier's ground, bounded by E2's list.
- **Judge.** A trace of system calls (number, information class, arguments, results) on the laptop against w2m's for
  the same program; the 68 families.
- **Open.**
  - **Known, not an experiment: how to trace system calls on Windows.** Microsoft ships DTrace for Windows; its
    syscall provider gives an entry probe and a return probe for every system call, with the arguments as `arg0`,
    `arg1`, ... and the return value (Microsoft Learn, "DTrace on Windows"). The laptop's tracer is DTrace.
  - E3. *How many system calls and win32k calls does a frame make?* Settled by Hail to the Rainbow's DTrace trace on
    the laptop: calls per frame at 112 frames a second.
  - E4. *Which system calls do the games make?* E2's static answer checked against E3's traces of Hail to the Rainbow
    and BioShock 2.

### 4.4 The window manager and GDI (1,486 win32k system calls)

- **Source.** The stubs; user32's and gdi32's code above them; Microsoft's documented message and window semantics.
- **Edge.** win32k's code is kernel-mode (win32kbase.sys, win32kfull.sys) and is not run, so its calls are written:
  windows, messages and their queues, input delivery, cursors, display modes, and the GDI a game uses. E2 and E4 give
  which part.
- **Design.** win32k's calls in the guest runtime; windows as AppKit windows on the Mac's main thread (milestone P's
  window); input from the Mac delivered as win32k delivers it (raw input, keyboard and mouse messages). A message pump
  makes win32k calls every frame, so these are answered inside the VM (4.9).
- **Judge.** E3's traces; the window and message probes in `probes/`.

### 4.5 Other Windows processes

User mode reaches other processes as well as the kernel. Each process below is either run under w2m from the copied
executables, or replaced by an answer on the port it listens on. Public sources settle each one below: none of them
runs.

- **csrss.** kernelbase registers each process and thread with csrss over ALPC (the base server's port) at start-up.
- **DWM.** The desktop window manager composes every window, and a flip-model Present hands its buffer to DWM.
- **Services.** Audio (AudioSes to the audio service), COM activation (the RPC subsystem), the console (conhost),
  cryptography. For audio, the documented WASAPI interfaces (IAudioClient, IAudioRenderClient, with XAudio2 on top
  unchanged) are the smaller edge, on Core Audio.
- **Known: csrss's protocol.** ReactOS implements csrss and its base server from the published structure: the
  `BASESRV_API_NUMBER` list (BasepCreateProcess first), `BASE_API_MESSAGE` and its requests (CreateProcess,
  CreateThread, ExitProcess, among others), and the generic `CSR_API_MESSAGE` over LPC (ReactOS `basemsg.h`,
  `csrmsg.h`, `basesrv/proc.c`). w2m answers csrss's port with those messages; csrss.exe does not run.
- **Known: DWM's part in presentation.** In the flip model every back buffer is shared with DWM, which composes from
  it with no copy; in the bitblt model Present copies the back buffer into a redirection surface; DirectFlip and
  independent flip let DWM step aside and put the game's buffer on the display directly (Microsoft Learn, "For best
  performance, use DXGI flip model"; DirectX developer blog, "DXGI flip model"). w2m has one window per Metal layer
  and nothing to compose against, so every Present is w2m's independent flip: the buffer goes to the CAMetalLayer.
  DWM does not run.
- **Known: audio's layers.** WASAPI is implemented in AudioSes.dll and MMDevAPI.dll; the Windows Audio service
  (audiosrv) sets up streams and policy, and the audio engine (audiodg.exe) mixes the shared-mode streams from the
  endpoint buffer (Microsoft Learn, "User-mode audio components"; "Windows audio architecture"). The edge stays at
  WASAPI's documented interfaces, on Core Audio; audiosrv and audiodg do not run.
- **Open.** E5. *Which other services do the two games reach?* A computation, not a search: E2's walk over the DLLs
  gives the RPC interface identifiers and ALPC port names they hold; E3's traces confirm them.

### 4.6 Graphics

- **Source.** Microsoft's Direct3D runtimes (d3d9.dll, d3d11.dll, D3D12.dll, dxgi.dll) do the API's work: validation,
  state and resource bookkeeping, exactly as on Windows. Below them each calls a vendor's user-mode display driver
  through an interface the Windows Driver Kit documents: the D3D9 interface (`d3dumddi.h`), the D3D10/11 interface
  (`d3d10umddi.h`, entry `OpenAdapter10_2`), the D3D12 interface (`d3d12umddi.h`). Shaders reach the driver as DXBC
  (Direct3D 10 and 11; its tokens documented in the WDK's `d3d11TokenizedProgramFormat.hpp`) or DXIL (Direct3D 12;
  LLVM bitcode, specified in Microsoft's open DirectX Shader Compiler repository).
- **Precedent.** Mesa's d3d10umd, VMware's Direct3D 10 user-mode driver over llvmpipe, about 12,700 lines, ran under
  Microsoft's runtime on Windows and once passed Microsoft's HCK wgf11 tests at 100% (Mesa merge request 10687). Mesa
  removed it in 26.3 because it emitted TGSI rather than NIR. The route has been walked once, to certification.
- **Edge.** One user-mode display driver of w2m's per interface generation (three), drawing with Metal. Shader
  translation: DXIL through Apple's Metal Shader Converter; DXBC first to DXIL through `dxilconv`, the DXBC-to-DXIL
  converter in Microsoft's DirectX Shader Compiler repository. Its converter (`DxbcConverter.cpp`, 8,316 lines, last
  changed 2026-04-07) has a case for 229 of the 231 opcodes in the DXBC opcode enum; the two without one,
  `D3D11_SB_OPCODE_ABORT` and `D3D11_SB_OPCODE_DEBUG_BREAK`, fall to `HandleUnknownInstruction` ("not yet
  implemented"). Direct3D 9 shaders (shader models 1 to 3) are not DXBC, and DXIL does not cover them, so dxilconv
  does not take them: the D3D9 driver needs its own translator from the D3D9 token format (`D3DSIO_*` in the SDK's
  `d3d9types.h`) to Metal. The kernel's graphics calls (D3DKMT, in win32u) for adapters, allocations and presentation.
  Presentation through DWM (4.5).
- **Why at the driver interface.** Microsoft's runtime keeps every API rule exact, and three driver interfaces cover
  four Direct3D versions. DXMT (permitted) translates Direct3D 11 at the API level to Metal; it is a judge of the
  driver's output and a measure of Metal, not the design.
- **OpenGL and Vulkan.** opengl32.dll and vulkan-1.dll load a vendor's installable driver the same way; one of each on
  Metal closes them, after Direct3D.
- **Judge.** Three: Microsoft's own graphics conformance tests for drivers, run against w2m's driver; the same frame on
  the laptop and in w2m, compared (milestone P's frames); the driver-interface trace against the laptop's real driver.
- **Open.**
  - **Known, not an experiment: how the runtime finds the driver.** The display adapter's registry key holds
    `UserModeDriverName` (REG_SZ), the path of the user-mode driver DLL; the runtime loads it and calls its exported
    `OpenAdapter` (for the 10/11 interface, `OpenAdapter10_2`), passing its interface version and the
    `pfnQueryAdapterInfoCb` callback (Microsoft Learn, "Initializing communication with the Direct3D user-mode display
    driver"; "Adding software registry settings"). w2m's registry and adapter answers are written to that.
  - E6. *Which D3DKMT queries does d3d11.dll make before it reads the key?* The documentation names the key, not the
    kernel queries around it. Settled by d3d11.dll's start on the laptop under DTrace (E3's tracer).
  - E7. *Which interface functions does each game use?* Settled by the driver-interface trace on the laptop.
  - E8. *Do the games' shaders convert?* Opcode coverage is read from dxilconv's source (above). The shaders' file
    format is published: a DirectX container is a header and a sequence of parts, among them RDEF (resource
    definitions), SHEX (DXBC bytecode) and DXIL (LLVM's "DirectX Container" documentation). What no source shows is
    whether each of these games' shaders passes the chain. Settled by the census of shaders in the games' assets,
    each put through dxilconv and Metal Shader Converter, counted converted and refused.
  - E9. *Which D3DKMT calls does one Present make on build 26200?* The flip model's design is published (4.5); the
    call list is this build's. Settled by one Direct3D 11 swapchain's Present under DTrace on the laptop.
  - **Known, not an experiment: where the conformance tests are.** They are the WGF11 tests of the Windows Hardware
    Lab Kit (WGF11 Blend, Filter, Render Targets, Resource Formats, among others), each with its prerequisites in the
    HLK test reference on Microsoft Learn. Mesa's d3d10umd ran them on llvmpipe.
  - E12. *Do the WGF11 binaries run outside an HLK controller?* Settled by one WGF11 test run on the laptop against
    its own driver, outside the HLK's job system.

### 4.7 Steam

Games call `steam_api64.dll`, which talks to the Steam client process; v0.2's goal includes Steam games.

- **Known: how Proton does it.** Proton's `lsteamclient` (ValveSoftware/Proton, 368 files) is a Windows-side
  `steamclient` whose every versioned Steam interface (ISteamClient006 to 023, ISteamApps001 to 009, and the rest) is
  a wrapper that forwards to the native client. The wrappers are generated, not written: `gen_wrapper.py` reads the
  Steamworks SDK headers of every SDK version (165 back through the 140s) with clang and emits one wrapper per
  interface version.
- **Design.** The same: a `steamclient64.dll` for the guest whose interfaces forward to the Mac Steam client, the
  wrappers generated from the Steamworks SDK headers by the same method. The Windows Steam client does not run.
- **Open.** E10. *Which interface versions do the two games ask for?* A computation: the version strings in each
  game's `steam_api64.dll` and executable.

### 4.8 32-bit games

- **Source.** SysWOW64's 32-bit DLLs and the WoW64 layer's (wow64.dll, wow64win.dll, wow64cpu.dll): on Windows a 32-bit
  process runs 32-bit DLLs whose system calls cross into 64-bit code that converts them.
- **Known: how WoW64 works.** A WoW64 process maps two ntdlls, 32-bit and 64-bit, and four 64-bit DLLs only:
  ntdll, wow64, wow64win and wow64cpu. The 32-bit ntdll's stubs make no system call; they call
  `Wow64SystemServiceCall`, which passes to wow64cpu (`CpupReturnFromSimulatedCode`) by a far jump to code segment
  0x33, the switch from 32-bit compatibility mode to 64-bit mode; wow64.dll and wow64win.dll convert the arguments and
  call the 64-bit ntdll and win32u (Mandiant, "WOW64!Hooks: WOW64 Subsystem Internals and Hooking Techniques";
  SentinelOne, "Deep hooks: monitoring native execution in WoW64 applications").
- **Design.** Run Microsoft's conversion: the 32-bit DLLs in the CPU layer's 32-bit mode, wow64.dll and wow64win.dll
  as 64-bit code, over the one 64-bit kernel of 4.3. w2m supplies only the mode switch: the translator treats the far
  jump to segment 0x33 (and wow64cpu's return to 32-bit mode) as a change of decoding mode. No 32-bit system call is
  written. E13 is retired.

### 4.9 Speed

- **The measure.** The laptop runs Hail to the Rainbow at 112 frames a second, 41 million instructions a frame over
  six threads, the busiest 11.9 million (recentering 2026-10-14). That count includes Microsoft's code, since it was
  measured on Windows. It does not say how often a frame enters the kernel; E3 does.
- **Design.** The compiler inside the VM (one vCPU, Sprints 083-084: 370 million instructions a second at the start,
  from 36); every system call answered inside the VM, without an exit to the host; several vCPUs; the ahead-of-time
  cache; the compiler's passes.
- **Judge.** Frames a second, seconds to the first scene, and exits to the host per frame, on every run, against 112,
  62 and E3's count.

## 5. The cutover

Once ntdll's loader replaces `loader.py`, nothing runs until three things work: ntdll's start-up, kernelbase's
initialisation, and the kernel's start-up set. The two paths therefore live side by side. Today Hail to the Rainbow
runs 80.9 billion instructions on the old path (frontier 1791942295792627000); that path stays the game's path of
record until the new path passes it. Each probe and family moves to the new path only when its system-call trace
conforms to the laptop's and its family rows reproduce. The 338 services stay until then, as the old path and as a
second opinion.

## 6. The order

0. Copy all of `C:\Windows` and the two hives into the depot (section 3).
1. E1, E2, E3 (no implementation). They size the kernel and win32k, and fix the judge. Each is a sprint with its
   question and settling result on its card.
2. The kernel's start-up set (E1's list): a probe runs to its entry on ntdll's own loader; csrss's start-up messages
   answered (4.5).
3. The kernel by manager, ordered by E2 and E4; the 68 families moved over one by one; then win32k's set; then the
   other processes and services (E5).
4. Graphics: E6, E9, E12; the Direct3D 11 driver and its shaders (E8) for Hail to the Rainbow; then Direct3D 9 for
   BioShock 2; then Direct3D 12.
5. Steam (E10).
6. 32-bit (the decoder's mode, the mode switch at segment 0x33, Microsoft's wow64 DLLs; 4.8).
7. Speed throughout: the compiler's chain, several vCPUs, the cache.

The compiler's chain (Sprints 089-091) goes on beside 1, since the CPU layer is the same in either design.

## 7. The exclusion

"Any game" excludes games whose anti-cheat runs as a kernel-mode driver: it loads into ntoskrnl, which this design
never runs. Every other game is in scope.

## 8. Risks, named

- **Kernel semantics.** The system calls are a list, but each call's meaning, class by class, is the kernel's code.
  Documentation and the DLLs' own use cover most; the laptop settles the rest. The risk is volume, and E2 measures it.
- **win32k.** 1,486 calls, the larger edge; E2 and E4 bound the part games use.
- **Processes.** w2m answers csrss's port from ReactOS's message set; a message the set lacks on build 26200 is a
  frontier stop at that port.
- **Driver interfaces.** The WDK documents them; a real driver's behavior under the runtime is learned from the
  laptop's traces (E7) and Microsoft's tests (E12).
- **The cutover.** Nothing runs on the new path until start-up works; the old path stays the record (section 5).
- **Build to build.** System call numbers change between Windows builds; w2m takes them from one build's copied ntdll
  and win32u (26200), so the DLLs and the numbers agree.
- **Speed.** Translated Microsoft code on every call, and every kernel entry inside the VM or the frame rate falls;
  measured from the first probe against the 112 frames.
