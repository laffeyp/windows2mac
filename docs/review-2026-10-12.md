# Review 2026-10-12 — the whole project, and a roadmap to close what it finds

Question: what w2m is, what it draws on, what is new in it, what is plainly wrong and plainly right, whether its code is well built, whether it follows `sdd-kit-3`, whether it uses substrate for what substrate is, and which well-known principles of binary translation and emulation it sets aside. The second half places every finding in a sprint.

## Method

Read in full: every text file of `sdd-kit-3/` (AGENTS.md, README.md, CLAUDE.md, TECHNIQUES.md, ADDENDUMS.md, ADDENDUM_PROMPT.md, both process-not-prompt files, foundations 01–04, grammar/, templates/, handoffs/, lib/sdd.py, and example/ with its sources, tests and fixtures; the nine `.pyc` files are bytecode and were not read); `windows_to_macos_research_direction_v0_2.md`; `WORKING_AGREEMENT.md`; `docs/plan.md`; `KIT_DIARY.md`; `docs/review-2026-10-11-ground-up.md`; Sprint 064's card; BLACKBOARD's Decisions, Deferred, Open questions, Drift watchlist and the head of Sprint tail. Two surveys, one of the code and one of substrate's use, read `src/w2m/`, `scripts/`, `tools/`, `tests/` and `./substrate`; their main claims were checked here by command before use.

Commands run at 648fe7ed (branch `sprint-065`): `uv run pytest` (8 failed, 2,066 passed, 109.87 s); `ruff check` (clean); `mypy` strict (clean, 378 files); `python3 scripts/gen_decoder.py --check` (exit 1); `gh run list --workflow ci`; `scripts/check_replay.py`; greps for `EnTSO`, `ACTLR`, `flush_translations(`, `runneradmin`, `w2m_file_stat_full`, `uncommitted`, and the `-dirty` stamp across `store/runs/`.

## 1. Verdict

w2m is honest and fast, and its judging regime is the best thing in it. In 471 commits over six days the frontier went from 13 instructions to 23.4 billion, and from 4.0 to 442 million instructions a second. Every instruction class answers to a named Intel CPU and every Windows family to rows a probe printed on Windows.

Four things are wrong at the root. The machine runs on one vCPU. Translated code is never invalidated while the game's logic is code Mono writes and patches. The harness's own records pass failures as successes in three places. And substrate keeps the records but runs none of the work. The branch under work is red.

## 2. What the project is

w2m runs an unmodified Windows x86-64 game, Hail to the Rainbow (Steam app 1699230, Unity 2019.4.40f1, Mono), on an M5 Max under macOS 26.5.1.

- **Decoder.** `x86dec.py` over tables generated from `specs/x86_decode.json`, judged by Intel XED v2026.08.23 and Capstone 5.0.9.
- **Lifter.** `lift.py` and `rules/` turn each instruction into explicit operations. `runtime.py` executes those operations in Python and is the model the VM is checked against.
- **Translator.** `vm_backend.py` compiles up to 64 instructions to the first branch into AArch64, appended to a 64 MB code cache inside a Hypervisor.framework VM at EL1. An in-guest dispatcher with a 2^20-entry hashed table finds the next block; a miss exits (`hvc #1`) to Python, which compiles it.
- **Guest runtime.** 268 Windows functions in freestanding C (`tools/guest_runtime/`, 47 files), linked into an MH_PRELOAD image the VM loads.
- **Host.** Python serves the thread scheduler (`scheduler.py`, `hvc #12`), files (`file_bridge.py`), virtual memory, module loading, and objects shared between processes (`kernel.py`), each by an exit over the monitor's text pipe.
- **Judges.** Each instruction class is judged case by case against the Xeon 8573C on GitHub's Windows runners; each Windows family against probe rows from Windows Server 2025 and 2022; since Sprint 060, the frontier's call stream against the game's own calls on Windows.

The frontier stops at mono's first x87 `FLD m64` (`dd 44 24 f8` at 0x1180ccfd2f), which Sprint 065 is lifting. Nothing has been drawn.

## 3. Influences

- **The kit (SDD):** sprint cards with signal, artifact and observation contracts; BLACKBOARD; KIT_DIARY; resolve-and-record.
- **Differential testing of emulators and decoders:** XED as decode judge, the CPU as semantics judge; Paleari et al. (ISSTA 2010) for decoders; Knight and Leveson (1986) for why two implementations from one specification are not independent.
- **Wine:** Windows structures in guest memory at Windows layouts; one host broker for shared objects, as wineserver is; probes in place of conformance tests.
- **Rosetta 2, FEX and box64:** reconstruction of x86 state at fault points.
- **Apple's guest TSO control** (`ACTLR_EL1.EnTSO`) and the macOS 26 4 KB IPA granule: the case for a VM backend.
- **CompCert-style contracts** over observable behaviour, from v0.2 §3.
- **Substrate:** the record of every run.

## 4. What is new

The judging regime, not the translator.

- **Mutation testing of the judges.** 196 planted faults in `scripts/family_run.py`, each naming the rows it must change, checked to land on code the run executes (KIT_DIARY #46, #49) and with its anchor text gated on every push (#48).
- **A CPU model, not a vendor, as reference.** AMD's EPYC parts and Intel's Xeons return different RCPPS and RSQRTPS tables (#32).
- **The game's own Windows calls as a judge** the family writer has not seen (Sprint 060): 790 first divergences reduced to five real defects without widening a relation (#50).
- **A Windows runtime built without Wine,** its behaviour taken from probe rows, its CPU semantics from a model judged instruction by instruction against Intel. No earlier Windows-on-Mac project is known to be built this way.

KIT_DIARY #14–#51 is the most useful file in the repository: each entry names a way a check fooled its author, with the run that showed it.

## 5. What is plainly right

- **External oracles with planted faults.** Sprint 037's 66-prefixed PUSH (RSP moved by 8, not 2) passed lockstep and the state differential, because both sides ran `lift.py`; the CPU caught it on its first run.
- **The backend chosen on measurement.** The message-passing litmus gave 2,245 forbidden outcomes in 50M with EnTSO off and 0 with it on (Sprint 009). A macOS process cannot protect 4 KB pages (`mprotect` returns EINVAL); the VM enforces them in hardware (Sprint 012).
- **No silent success.** An argument shape no row covers calls `w2m_unimplemented` (`runtime.c:46`) and stops the run. A scan of short service bodies found no blind `return TRUE`.
- **Static checks.** Strict mypy and ruff pass on 378 files. Every encoder form is assembled by clang and compared (`tests/test_a64_encoder.py`).
- **Speed work that counted first.** Sprint 064 found 8,474,510 of 8,747,587 exits were dispatch misses from a 4,096-entry table indexed by the low 12 bits. Fixing it gave about a hundredfold.

## 6. What is plainly wrong

### R1 — The branch is red

On `sprint-065`, CI failed on 9 of its last 10 pushes, every one at `gen_decoder.py --check`: commit 68339160 moved the decode spec to 0.9.0 and did not regenerate `src/w2m/x86dec_tables.py`. The local check exits 1 as well. `uv run pytest` fails 8 tests:

- four in `test_runtime_native.py` that do not compile: the test stubs declare `w2m_file_stat_full` with two arguments, the C files with three. The 17 `u64 w2m_*(...);` prototypes declared inside 13 `.c` files, instead of once in `runtime.h`, let the signatures drift;
- three that pin committed records by sha256 (`file.c`, `static_tls`, FCOS) and break on any edit to the source they pin;
- one in `test_call_trace.py`, a file-namespace stop on a temporary file the listing does not record.

KIT_DIARY #33 set the rule "read the CI conclusion of each push before the next push". This sprint breaks it.

### R2 — One vCPU

All guest threads run on one vCPU, switched by Python every 200,000 instructions (`scheduler.py:25`). Each process is its own VM, and the VMs are driven round-robin from one Mac thread. `EnTSO` is set nowhere in `vm_backend.py` or `vm_monitor.c`; it exists only in `probes/mac_hv_litmus` and `probes/ordering_cost`. That is sound while one core runs. Unity starts 4–6 job workers and 16 background workers. Milestone C's 16.7 ms frame cannot be met on one core, and the TSO, split-lock and LOCK-ordering questions return on the day a second vCPU is added. No plan row holds that day.

### R3 — Translated code is never invalidated

`flush_translations` (`vm_backend.py:1160`) is the only path that drops a block, and only `scripts/vm_oracle.py:210` calls it. No write, VirtualProtect or VirtualFree of translated code invalidates anything. The game's logic is code Mono generates into RWX memory and patches in place; the frontier already runs it. Plan row 067 holds this work behind milestone-A-adjacent sprints. A full cache raises `CompileError("code cache full")` (`vm_backend.py:2299`) instead of evicting.

### R4 — The harness passes failures

- **Run status is ignored.** No w2m code reads `RunResult.status`; `run_frontier.main` returns 0 (`run_frontier.py:259`). `store/runs/` holds 8 records finalised `stuck_quiescent` and 7 with a `ProducerFailed`, among them `class-add_lock-1791663118796268000` and `family-files_more-1791701843956559000`. Only `judge_traces.py:205` checks for failed producers.
- **The replay gate counts containers.** `check_replay.py` reports 9,017 intact. `assert_replayable` on `store/runs/file-generation`, a directory of records, returns `frame_count=0, complete=False` without raising; the script catches only exceptions, so the container counts as intact and the records inside it are never checked.
- **Most records do not name the code that made them.** 7,196 of 9,017 records carry a `w2m_commit` ending `-dirty` (class 5,545, family 1,607, file 28, frontier 15); 452 carry no stamp. `uncommitted()` refuses a dirty tree only in `run_frontier.py` and `record_game_run.py`; `class_run.py` and `family_run.py`, which wrote most of the store, have no such guard.

### R5 — The translator's hot path

- The translator is Python, run at each dispatch miss.
- Every exit crosses a text pipe carrying 31 hex registers per `set`/`exit` (10.3–10.5 µs, Sprint 048). Plan row 045, the transport, has waited since 2026-10-10.
- Blocks are not chained: every block exit, direct or indirect, goes through the dispatcher's table.
- Flags are eager: CF, ZF, SF, OF and PF in x19–x23 are recomputed after every flag-setting instruction (`_set_flags`, `vm_backend.py:348`; PF alone about eight instructions). No liveness pass removes the dead ones.
- The slow path (`hvc #10`, `#11`; x87, integer-model ops, unmasked SSE faults, misaligned LOCK, narrow DIV) builds a fresh Python `Runtime` for each step (`_slow_sse`, :2169–2217).
- Every block entry does a read-modify-write on an instruction counter (:2288).
- A read of a flag the SDM leaves undefined stops the run (`hvc 0x40`, :494). That is strict, and a real program can trip it.

### R6 — The reference machine is built into the product

`C:\Users\runneradmin` is written in `vm_backend.py:240`, `file_bridge.py:59–64` and `known_folders.c:10`; the runners' four processors and their 1024×768, 96 DPI display are written into the guest runtime. Matching the reference is the user's decision of 2026-10-11 and stands. The values belong in one profile file that the guest, the host and the judge all read, so that the gaming laptop of Decision 2026-10-11 becomes the reference by one file, not by edits in several.

### R7 — Graphics, audio, input and Steam are untouched

DXGI and MMDevAPI are COM objects with fixed answers; the DXGI vtable lists `CreateSwapChain` and nothing behind it runs. v0.2 §10 (DXBC to Metal, command translation, resource planning, a command ring across the VM boundary) has one paragraph in plan phase 6 and no design.

## 7. Code structure

The pieces are in sensible homes; three files have outgrown theirs.

- **`vm_backend.py` (2,835 lines).** It holds the address layout (:67–260), the instruction compiler (`compile_insn`, :640–950, one `if k ==` chain over about 30 operation kinds), the `VM` class with process setup, PEB, COM vtables, threads, the host-request switch and the run loop (:1050–2588), and harness drivers: `lockstep` (:2610), `state_differential` (:2667), `measure_exits` (:2327), `record_translations` (:2792), and `REQUEST_FILES` for `family_run` (:217). `ASYNC_STOP_RULE` (:260) and `CVT_INDEFINITE` (:614) are switches kept only so a test can show the wrong choice fails. Codegen, layout and request server are the seams.
- **`runtime.py` (1,148 lines)** is ordered by sprint: `_sse_049b` (:466), `_sse_050` (:542), `SSE_049B`, `IMPLICIT_050`; `semantics_differential.py` carries `_fixed_050` to match.
- **`family_run.py` (2,974 lines)** is about 2,100 lines of data: 58 `Family(...)` and 196 `Plant(...)` literals with run ids and sha256s inline. That data belongs in JSON beside `contracts/`.
- **Product code lives in `scripts/`.** `pyproject.toml` has no `[project.scripts]`; the game starts through `scripts/run_frontier.py` and `family_run.run_in_vm` (:2604). Seven test files import scripts as libraries; 22 scripts patch `sys.path`.
- **Duplication.** `item_run` is defined in `class_run.py`, `family_run.py`, `file_run.py` and `model_family.py`; `sh()` in six scripts. `file_run.py:135` is an older copy of `family_run`'s pipeline.
- **An import cycle.** `rules/_vex.py:22` and `rules/_sse.py` import `vm_backend`; `vm_backend` imports `rules` lazily (:917).
- **Rule files as identity.** 243 of the 250 files in `rules/` are 11 lines or fewer (`rule = _int.alu`); they exist to give each class its own sha256. A hash over each rule's function and the helpers it calls gives the same identity without the files.
- **Stale names.** `vm_backend.py:3` calls itself `vm.py`; `a64_encoder.py:3` calls itself `a64.py` and points at `tests/test_a64.py`.

Substrate is load-bearing as a record format and decorative as an orchestrator.

- **The record.** All 9,017 records under `store/runs/` are written through `w2m.record.run_with_provenance` (30 call sites); `src/w2m` imports only `substrate.api`. - **The orchestration.** No w2m code uses a View, a Route or `embedded_substrate`. `run_frontier.py:209–226`, `family_run.py` (2898–2909) and `class_run.py` (208–220) are fixed chains with `lambda c: True` predicates and `input_builder=lambda c: {}`, passing data through closures and files on disk. Written as plain Python that appends JSONL they would behave the same. Only the candidate loop branches, and its triggers read a mutable `Session` (`run_candidate_loop.py:262–279`, 362–378), so the record cannot show why a trigger fired. The 2026-10-11 review's S2 and S3 stand.
- **Status, replay and provenance** as in R4.
- **The clone.** Branch `w2m` at 3c0542a equals `origin/main` as last fetched; it carries no w2m kernel changes. Upstream main has moved to `abe17cee`, not fetched. `substrate-bash-fix` is a sparse worktree on `fix/bash-tool-timeout` (418c027e), unmerged and probably superseded by `tools.py:404–443` (not tested).
- **No misuse of models.** No Responder sits on a judging path; models only write candidates. No blob exceeds 1 MB.

## 10. Principles of the domain set aside

- **Code-cache coherence.** QEMU, Rosetta 2, FEX, box64 and DynamoRIO invalidate translations on a write to translated pages. w2m does not (R3).
- **Block chaining.** Direct branches are patched to jump to the next translated block, so steady-state code does not return to the dispatcher. Every dynamic translator since Dynamo (2000) does it. w2m does not (R5).
- **Lazy or liveness-pruned flags.** QEMU, Rosetta 2 and FEX compute flags only where they are read. w2m computes all of them every time (R5).
- **Amdahl's law.** A one-thread frontier at 442 MIPS says nothing about a frame drawn by twenty threads (R2).
- **Reuse of an existing conformance suite.** Wine's per-DLL tests (`dlls/*/tests/*.c`) were named as an evidence source on 2026-10-07 and are unused (feasibility review S1). They are the cheapest answer to KIT_DIARY #47: rows that copy the game's inputs prove the code on those inputs only.
- **Generated code under a `--check` gate** works only when the generator runs on every commit (R1).
- **Configuration apart from code.** Facts of one machine are written into the product (R6).
- **`robots.txt` placement.** A `robots.txt` at a repository's root is never read by crawlers; only `github.com/robots.txt` applies.
